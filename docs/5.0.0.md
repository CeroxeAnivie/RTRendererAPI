# RTRendererAPI 5.0.0

5.0.0 is a breaking, general-purpose rendering API release on `main`. Delivery targets are GitHub source and signed Maven Central artifacts.

The API remains host- and domain-neutral. Its public model contains no application, game, engine, block, or domain-specific light types. Java 25 is the published source and bytecode baseline.

## Changes

- Unified renderer creation at `Renderer.open(...)` and configuration at `RendererConfig.builder()`, with explicit `recommended()` and `presentation()` policies. Removed the redundant bootstrap/preset route and the unreferenced `VulkanRendererRuntime` execution path.
- Added public retained-scene GLSL replacements for ray-generation, miss, closest-hit, and any-hit stages. Applications can declare ordinary read-only std430 storage buffers and supply immutable `ResourceData` per frame. The generic graphics, compute, triangle RT, and procedural RT command APIs remain available for workloads outside the retained-scene topology.
- Added native-format CPU frame views, explicit immutable snapshots, origin/stride/provenance metadata, and scoped mapped reads. HDR and integer bytes are not implicitly converted. Added direct `ByteBuffer` buffer upload and reusable descriptor scratch for programmable scene data.
- Updated the Demo, migration/reference guides, independent Maven consumer, ABI baseline, dependency verification, release checksums, and Java 25 CI configuration.

## Frame-generation acceptance

A requested multiplier or a healthy SDK status is not proof of generated output. Acceptance requires all of the following:

1. The renderer window is the actual Windows foreground window. GLFW's cached focus bit alone is insufficient.
2. Real application frames with valid scene motion, depth, motion vectors, constants, and frame markers reach the proxy present path.
3. `slDLSSGGetState` reports the requested configured multiplier and healthy status, with zero state-query failures and zero generation-request misses.
4. Authoritative `numFramesActuallyPresented` evidence proves the requested generated-frame count for at least 12 consecutive presents. After the first generated frame, observation continues for at least five seconds.
5. Renderer and presenter close normally; the process exits with code zero.

The native acceptance gate runs for at most 60 seconds and reports elapsed time, actual base FPS, foreground/focus observations, generated output, multiplier, native status, and query/miss counters. If it does not observe the window in the foreground for five cumulative seconds, it reports `ENVIRONMENT_NOT_FOREGROUND`: this is inconclusive environment evidence, neither a pass nor a hardware/API unsupported result. If sufficient foreground time exists but generated output is absent or unsustained, the strict output gate fails with the observed diagnostics.

The foreground distinction is based on direct observation on this machine. An earlier 60-second run delivered 3,594 base frames and zero generated frames while reporting only GLFW focus. In the paired foreground run, Windows reported zero foreground presents during the first 10 seconds and generation remained zero. After the window was brought to the foreground, generation started and sustained 2x for 302 consecutive foreground samples. MFG 3x subsequently produced 584 generated frames in 292 foreground samples. The user confirmed that the earlier window had been left in the background. Background zero-output runs are therefore classified as presentation-environment failures, not evidence of a broken renderer.

Streamline's current Vulkan path supports fixed MFG multipliers on this device. The SDK programming guide documents Dynamic MFG as D3D12-only; adaptive API policy must not be interpreted as proof that Vulkan Dynamic MFG is available. The adaptive gate above records the fixed cadence Streamline actually selected.

## Performance and limits

The GPU scene throughput gate previously measured three 1080p runs at 410.79, 333.61, and 297.94 FPS (GPU average 2.870 ms), with three windowed runs at 338.66, 228.21, and 218.20 FPS. These are bounded local measurements, not guaranteed application throughput. Cold pipeline creation on this driver took about 166.5 seconds; warm throughput excludes that startup cost.

The implemented backend targets Windows, NVIDIA RTX hardware, and Vulkan. AMD, Intel, Linux, macOS, D3D12, Metal, software rendering, cross-driver stability, and arbitrary host-engine integrations were not certified by this acceptance run. GPU tests require an interactive foreground display for frame-generation acceptance; do not infer feature failure from a headless or background-window run.
