# 7.1.7

兼容修复，Java公共API与传输契约保持不变。

- 内存场景更新在修改场景前为TLAS、sub-instance与三张GPU TLAS辅助表预留共享heap存储；压力下整体延后准入，不在半完成的场景上继续。
- 容量按几何级数增长，数量减少不重建辅助buffer。已完成双队列fence的TLAS立即进入独立复用池，不再等待同代所有mesh的分批回收。
- 必需的dense geometry迁移与receiver属性更新按连续行归并上传；保留全SDK场景准备与场景语义。
- DEEP六项GPU工作计数在每线程精确累计，再按活跃wave汇总写出，减少遍历内全局原子竞争；不关闭计数或减少光照工作。
- 整场景reset先清理借用旧graph的节点索引、GPU表与cull binding，再释放旧资源所有权，修复重复reset后旧节点指针失效导致的原生崩溃。普通增量路径不增加清表或waitForIdle。

当前原生DLL为`e19ef2868f6c26b32946fcb8caf8102b52fbeadab455cc7054833a684248d35d`。受影响的10项原生正确性检查均实际exit0，包含重建、拓扑、准备取消、资源arena、输出租约及真实GI RR。独立参考目录只把同DLL使用的计数shader恢复为原始逐事件全局原子：15个场景的六项整数计数全部相同，80份HDR文件逐字节一致，参考Java进程exit0。参考shader没有覆盖默认运行目录。

通用容量回归使用1个可见对象与512个视野外对象。连续两批各删除146个对象、四轮同容量增删往返都未分配新的TLAS或三张辅助表；146仅是测试规模。存在两代mesh回收积压时，已完成双fence的TLAS仍回池212,992字节。共享mesh替换、纯transform零TLAS／辅助表申请均通过。旧输出租约的四个GPU纹理平面在场景和相机更新前后逐字节不变，同时确认新输出确实发生变化。一次属性更新记录为440行、12次writeBuffer；这是上传归并机制证据，没有旧版同条件时延数据。

初次reset回归暴露旧graph索引悬空，调整JVM参数重试仍失败后修复，保留两次失败日志。输出租约测试初版错误地假定关闭太阳一定改变gain，改用相机转离场景后通过，未放宽比较。原子参考初次复制遗漏空的Assets/EnvMaps目录，SDK枚举该目录抛异常后又触发既有初始化失败清理缺口；补齐参考目录后通过。这个清理缺口尚未修改，不归为本次生产回归。运行时若在HostRenderPass创建完成前失败，`Session::shutdown`仍可能解引用空指针。

本批仅运行受影响的正确性与制品验证，初始GPU占用45%，不用于绝对性能结论。用户要求子代理交付后暂停，未接入MC、未补跑7.1.6、未跑新旧性能矩阵，不承诺FPS或延迟收益。必要SDK dense场景准备仍完整保留，不能把容量复用说成消除了全表扫描。完整GPU P95≤4ms仍未达标。证据索引见`docs/quality/data/native-resource-chain.json`；完整制品检查见`tools/Verify-NativeResourceChainRelease.py`。
