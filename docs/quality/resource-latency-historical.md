# 资源长尾修复验收

历史验收版本：7.1.5。本文保留此前 13 项正确性、36/36 个有效性能窗口及对应发布身份，不是当前本地 `80803215…` DLL 的全量验收。**当前性能优化已停止，完整请求 GPU P95 为 5.422623 ms，4 ms 未达；当前身份、全部前后对照和 N01～N09 未完成项见[收尾记录](optimization-closeout.md)。** 本文 CPU 稳态与普通局部预算未通过的项目继续保留，不把采集完成写成性能达标。

历史矩阵包含 27 个当时最终 DLL `d32209b4…` 窗口，以及按用户要求保留的 9 个先前通过窗口。后者仅在 719 档 stable／animation／local，原 DLL 身份及保留理由见 [保留清单](data/resource-latency-retained.json)。不能把它们改标成当前 DLL 重跑。该历史矩阵的 shader 和依赖 DLL 保持相同；首次 OFF／SUMMARY stable 还保留了解码修复前的 Java 类身份。

历史机器可读记录：[resource-latency.json](data/resource-latency-historical.json)。当时 JAR、DLL、shader、PDB、POM 与 Gradle metadata 身份：[resource-latency-release.json](data/resource-latency-release-historical.json)，该自哈希清单只存在仓库，不嵌入 runtime ZIP。本次不覆盖这份发布证明。原始逐请求、旧渲染区间 GPU、诊断 GPU scope、资源压力与执行日志留在 `build/reports/resource-latency`，每份输入有 SHA-256。

## 可比较的收益与历史边界

本批相同内容、相同质量的三模式对照可以量化诊断成本。以下取稳定窗口：

| mesh | DEEP → SUMMARY FPS | 吞吐变化 | 旧渲染区间 GPU P95 变化 |
| --- | --- | ---: | ---: |
| 719 | 180.67 → 232.47 | +28.68% | -20.41% |
| 977 | 136.57 → 184.57 | +35.14% | -25.75% |
| 4096 | 137.15 → 185.15 | +34.99% | -25.24% |

这是模式差异，不是旧版升级倍数。旧最终包在 MC 的 DEEP 完整 GPU P50/P95 为 7.2064/9.27056 ms，移动 UPDATE P50/P95 为 2.9819/35.5332 ms、最大 98.817 ms；其内容、相机和流入 trace 与通用夹具不同，只能作为历史参照，不算同场景加速百分比。旧 290.63 FPS 来自不同 DLL 且包含信号复用，不能替代最终包基线。

代码层面的可核对变化：后台交接固定 32×512 B 存储，不再为每个 enqueue 分配队列／shared_ptr；满槽不会搬走被拒绝对象。OFF recorder 的 100000 次自检没有 clock／allocation／新事件。CPU recorder 每次 submit 微基准 P50/P95：OFF 13.460/17.980 ns、SUMMARY 1345.880/1405.385 ns、DEEP 1467.530/1942.170 ns；它不是完整 API submit 或游戏帧率。稀疏源 oracle 共 7425 sample，最大 half-float 误差 0.0009764433。

## 生命周期、失败与修复后补验

冷启动至首个输出 10.636 秒、暖重开 9.767 秒；对应 device 阶段 9.532/9.194 秒，关闭 0.380/0.330 秒。这是早先通过的生命周期数据，未因追加代码重复跑；它不能计入稳态帧速，也不能证明全程从未卡顿。

4096 初次夹具因初始化环覆盖误判；改独立观察后又发现慢消费夹具未处理合法背压，已改 trySubmit 和 finally 归还。设备恢复后 4096 整档通过。另有一次 compute PSO 创建失败，在独立进程正常后仅重试该失败项并通过；底层原因未确定。

719 DEEP 正式窗口暴露 GPU CSV 无符号 FNV64 被 `Long.parseLong` 拒绝，已改无符号解析并补高位边界检查。成功的 OFF／SUMMARY 窗口没有为此重跑。

持续流入初次出现准入／GPU fence 超时，电脑重启后再次设备失败。转储符号链确认失败设备的 garbage collection 从 `SampleBaseApp` 析构中抛异常，最终 `terminate`／`abort`，已在设备失败时保留队列对象到 teardown，避免抛出完成查询异常。同时源码核对发现删除实例未进入退休所有权；现保留 detached node 和最后实例网格到 graphics／compute 都完成，仍有共享用户的网格不入池。修复后同一流入负载的正式窗口通过。该转储证明退出缺陷，不能据此推定初始 GPU 失败全部来自某个驱动缺陷。失败记录、转储 hash 与符号链见 [failure evidence](data/resource-latency-failures.json)。

系统曾记录 nvlddmkm 153，nvidia-smi 也曾不返回。前台 GPU 可运行与本进程能否创建设备是不同事实；遥测超时不被解释为整个 GPU 无响应。重启后初始占用 0%、显存约 120 MiB，无旧 Java 残留。重启还造成分析器文件内容全为 NUL，已从保存的实现恢复并扫描源文件；只补离线分析，没有重跑成功 GPU 窗口。

没有修改消费方工程、玩家目录、存档或配置。不使用 computer use，不开新子代理，不跑 FG/MFG。重任务串行，Windows Job 限制进程树 10 GB，日志保存峰值与退出状态。未做本轮 MC 实测，旧 GL 长调用也未复现，不能代签消费方最终帧率或宣称驱动唯一根因。
